## 提示词 1：课程顶部、为什么需要评测、什么值得测

```text
依据公共视觉规范生成第 1/4 张页面切片，右栏高亮第 1、2 节。主栏从上到下排列：

一、课程顶部
「← 返回课程目录」
「第 16 课  搭建评测飞轮」
「找到问题，有的放矢。」
「预计 25 分钟 · 系列：从 0 到 1 设计一个 Agent」
本课要点用三条短句：理解 Agent 评测的必要性；先定位高价值问题，再设计评测；把真实失败沉淀为回归集。

二、「1. 为什么需要评测」
用五条带线性图标的说明，保留五个原因：
- 非确定性输出：同一输入可能得到多个有效答案，评测是否落在可接受范围。
- 结果质量定义具有主观性：工程、产品、业务与用户共同定义标准。
- 独特的失败模式：幻觉、偏见、提示敏感性、提示注入和越狱。
- 衡量产品是否成功：任务完成、用户满意、异常与高风险场景。
- 定位问题，快速迭代：用量化反馈验证改进是否有效。
浅绿结论条：「评测的目标不是得到一个漂亮的分数，而是更快找到值得解决的问题，并确认改动真的有效。」

三、「2. 什么值得测」
「2.1 不需要一开始就测完所有环节」
五步短流程：跑通典型任务 → 结合执行链路与反馈定位问题 → 找到主要失败点 → 建立专项评测 → 稳定且低影响环节先保留观测。
小型对照：「机票已经预订」≠「数据库中真实存在订单」；强调「第一优先级：用户任务是否真正完成」。

「2.2 用四个问题判断优先级」
双列表格「判断维度 / 要问的问题」，四行：
业务影响 / 出错会影响什么？
发生概率 / 这个问题多常见？
不确定性 / 团队是否知道 Agent 能否稳定做好？
可改进性 / 测出问题后能否采取行动？
公式：「评测优先级 ≈ 业务影响 × 发生概率 × 不确定性 × 可改进性」
旁注：「高风险但低频：仍应提高优先级」。

「2.3 从三层结果中选择评测点」
三层横向图：最终结果（用户目标是否完成）→ 关键过程（重要节点是否做对）→ 运行约束（安全、耗时与成本）。
短结论：「10 个步骤 ≠ 10 套同等复杂的评测」。

「2.4 电商客服 Agent 示例」
问题：「我七天前签收的这件商品还能退吗？」
左右对比：
第一版优先检查：订单和签收时间；有效退货规则；商品类型与订单状态；不确定时转人工；需要退款时真实创建退款单。
可以暂缓：低频过渡语；两种有效工具调用顺序的差异；不影响理解的轻微措辞差异。

视觉重点是四维优先级表和三层评测图，其他内容用紧凑短句，避免重复卡片和大面积装饰。
```

```text
元信息小标签：任务类型、难度、风险等级、数据来源、首次出现版本。
```

## 提示词 3：评测方法、工具与平台

```text
依据公共视觉规范生成第 3/4 张页面切片，右栏高亮 3.3、3.4，顶部三步导航突出「03 方法和工具」。

一、「3.3 第三步：方法和工具」
先用小型分类图说明：执行方式分为「人工测试 / 自动化测试」；自动化评分可使用「代码规则 / LLM-as-a-Judge / Agent-as-a-Judge」。标注「实际项目通常组合使用」。

四个方法模块，统一包含用途、例子和局限，采用两列布局：

「人工测试」
产品、测试、业务专家和真实用户参与；适合标准建立、复杂业务判断、发现意外问题、校准评测器。
例子：业务专家检查退货承诺是否合理。
局限：慢、成本高、标准可能不一致；自动评测建立后仍需定期抽查。

「基于规则或代码的自动化测试」
检查 JSON、工具名称和参数、退款单真实状态、访问权限、耗时与成本阈值。
优势：快速、便宜、稳定，适合 CI 与回归；局限：难判断开放式表达质量。
强调：「能用程序验证，就不要让另一个模型猜」。

「LLM-as-a-Judge」
根据评分标准判断完整性、清晰度、依据、规则遵循，或比较两个版本。
评分提示词包含：评分对象、维度、等级、证据、信息不足时返回无法判断。
局限：风格、顺序与模型偏好可能影响分数；需人工标注样本校准。

「Agent-as-a-Judge」
具有工具与任务循环，主动获取证据后判断；例如打开引用来源核实结论，或查询数据库确认操作。
适合证据分散、复杂产物和完整执行轨迹。
局限：可能选错工具或漏看证据，成本与耗时更高；作为其他检查方式的补充，不能未经校准就独立裁决。

「如何组合评测方法」
原则：「优先使用成本最低、能够可靠判断问题的方法」。
四行映射表：
格式、字段、阈值、数据库状态 → 代码或规则
表达质量、语义正确性、是否有依据 → LLM-as-a-Judge + 人工校准
需要主动访问环境获取证据 → Agent-as-a-Judge + 确定性检查
高风险、标准不清楚或存在争议 → 业务专家人工评测
浅绿案例条：「代码检查退款单状态 + LLM Judge 检查用户解释 + 人工抽查高风险失败」。

二、「3.4 一些 Agent 评测平台和产品」
紧凑双列表格「平台 / 使用方式与特点」，保留五行：
LangSmith / Trace、数据集、离线与线上实验；代码与模型评分、人工标注
Langfuse / 可观测性与评测联动；云服务或自托管、数据集实验、线上评分
Arize Phoenix / 开源 Trace 分析、实验与评测；OpenTelemetry / OpenInference
Braintrust / 数据集、实验快照、评分器、CI 回归与线上质量监控
Promptfoo / 配置文件与命令行；本地或 CI 比较、规则断言、模型评分、Agent 轨迹检查

选型因素用六个标签：技术栈、自托管、数据能否上传、界面化标注、CI 接入、调用与存储成本。
提示：「平台不能替代业务目标、指标和用例设计；采用前重新核对当前版本、部署方式和价格。」

视觉重点是四种方法的对比，平台表作为补充。不添加厂商 Logo、价格或未提供的功能承诺。
```

## 提示词 4：注意事项、评测飞轮与练习

```text
依据公共视觉规范生成第 4/4 张页面切片，右栏高亮第 4、5、6 节，完成长页收尾。

一、「4. Agent 评测的注意事项」
用三组紧凑清单呈现九项，不展开成长段落，保留编号：

评什么、看什么：
4.1 评测整个 Agent 系统，不只是模型：结合提示词、上下文、知识库、工具、权限与环境定位原因。
4.2 不把“完成了”当成成功：检查真实邮件、日历、数据库或文件状态。
4.3 结果优先，也检查关键过程：越权、错误数据源、泄露、循环、异常成本与必需业务步骤。

可靠性与评测器质量：
4.4 一次通过不代表稳定：pass@k＝多次尝试至少成功一次；pass^k＝多次尝试全部成功。
4.5 先评测评测器：参考答案通过、明显错误识别、专家一致性、顺序与风格偏差、信息不足时无法判断。
4.6 平衡用例：应该做 / 不应该做，正常 / 异常，容易 / 困难，高频 / 低频高风险。

数据集健康与治理：
4.7 不在测试集上反复调到满分：保留独立验证集，用新流量检查，新失败进入回归集。
4.8 不让单一分数掩盖风险：「99 个普通问题正确 + 1 个高风险退款任务越权 ≠ 可以上线」。
4.9 控制数据、环境与版本：记录模型、提示词、工具、知识库、评测器、数据集版本；隔离状态，脱敏并控制权限与保留期限。

二、「5. 如何搭建第一版评测飞轮」
视觉重点为两列五行的编号步骤图，清楚连线并让第 10 步回到第 1 步：
1 选择任务：3～5 类重要用户任务
2 跑通流程：少量真实案例人工测试
3 定位问题：结合 Trace 找主要失败点
4 确定指标：主指标 + 安全、成本、延迟约束
5 建立用例集：20～50 条，覆盖正常、异常、高风险
6 组合评测器：代码 + LLM Judge + 人工复核
7 建立基线：记录当前版本表现
8 一次解决一类问题：优先处理高价值失败
9 运行回归：专项用例 + 核心任务集
10 上线继续观察：新失败进入回归集

下方短案例「退货咨询：过期规则问题如何进入评测飞轮」：
发现过期规则 → 按商品和订单状态分类 → 选典型案例 → 增加规则版本指标与用例 → 修改检索与版本管理 → 重跑专项及核心任务集 → 确认正确率提高且耗时、成本、转人工率未异常退化 → 上线观察。
结论条：「评测飞轮不是一次性做一份测试报告，而是不断把问题变成用例，把用例变成改进证据。」

三、「6. 练习题」
说明：「请选择你的 Agent 中一个最重要的任务，完成一张评测设计卡。」
用双列紧凑表单呈现十二个字段，每项留一行填写空间：
任务名称、用户目标、为什么值得测、成功结果、不可接受的失败、需要检查的最终状态、需要检查的关键过程、主指标、约束指标、第一批用例、评测方法、回归触发条件。
评测方法显示四个选项：人工 / 代码规则 / LLM-as-a-Judge / Agent-as-a-Judge。

页面底部显示「本课产出」及完整句子：
「一份 Agent 评测方案，明确高价值评测任务、指标与用例、评测方法和工具，以及从真实问题进入持续迭代的评测飞轮。」
右侧绿色按钮「进入下一课 →」。

注意事项用短句清单节省空间，飞轮保持十步，练习保留十二字段。不要重复课程顶部，不添加庆祝插画或装饰性大图。
```
