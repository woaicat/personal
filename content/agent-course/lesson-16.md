

## 1. 为什么需要评测
大模型独特的性质导致传统的软件测试已经无法全面评估相关产品的质量或用来定位系统的问题了。为了应对以下大模型所带来的特殊问题，评测必须存在：

1、非确定性输出：传统软件的输入与输出是固定的，而 LLM 对同一输入可能产生多种有效输出。因此评测的目标不再是验证唯一的正确答案，而是确保所有潜在输出都落在可接受的范围内。
2、结果质量定义的主观性：传统软件测试由工程团队负责；而LLM的输出，还需业务人员等非技术方评估；对于创意、摘要等生成式任务，也不存在唯一的“标准答案”。
3、独特的失败模式：LLM 带来的风险并非传统“bug”，而是需专门评估的特殊属性
幻觉：生成看似合理但与事实不符的信息。
偏见：学习并放大训练数据中的社会偏见。
提示敏感性：输入内容的微小变化可能会导致输出结果的质量剧烈波动。
提示注入和越狱：恶意用户可能通过精心设计的提示词，绕过模型的安全护栏，诱使其生成有害或被禁止的内容，或者泄露其训练数据或上下文中包含的个人隐私或商业机密
等等其他可能的失败模式

3、衡量产品是否成功：当我们需要说服非技术背景的业务人员参与评测，或者说服领导层支持评测，最核心的问题是：我们为什么要投入资源进行评测？一个健全的评测体系能够清晰地将抽象的指标与具体的业务成果联系起来。通过评测可以回答以下关键问题：
当前产品是否能满足我们定义给它的特定任务和需求，满足到什么程度？
用户使用情况是否符合预期？用户满意度如何？
产品或系统运行的怎么样？能够应对状况之外的场景或问题吗？能覆盖边缘和风险情况吗？

4、定位问题快速迭代：如果没有良好的评估体系，团队很容易陷入“原地打转”的困境，不断地进行修改，却无法确定这些修改是否真正提升了产品性能。评估体系为每一次迭代提供了必要的“量化反馈”，验证了关于改进的假设是否成立，并确保了团队在正确的方向上前进，形成“构建-部署-评估-记录-迭代”组成的快速、可验证的循环。

```text
真实运行
  → 发现问题
  → 选择高价值问题
  → 建立评测用例与指标
  → 修改 Agent
  → 回归测试
  → 上线观察
  → 发现新的问题
```
评测的目标不是得到一个漂亮的分数，而是更快找到值得解决的问题，并确认改动真的有效。

## 2. 什么值得测

### 2.1 不需要一开始就测完所有环节

一个 Agent 可能包括模型、系统提示词、上下文、知识检索、记忆、工具、多 Agent 协作、权限控制和前端交互。一次任务还可能经历很多轮判断和行动。

如果一开始就为每个组件、每个步骤都建立完整评测，工作量会很大，而且团队可能花了很多时间测一个并不影响最终结果的环节。

更现实的顺序是：

1. 先用少量典型任务跑通完整流程。
2. 结合执行链路、人工体验和用户反馈定位问题。
3. 找出对任务结果影响最大的失败点。
4. 围绕这些问题建立专项评测。
5. 暂时稳定、影响较小的环节，可以先保留观测，不急着投入复杂评测。

Anthropic 将一次 Agent 评测中的完整记录称为 transcript、trace 或 trajectory，并特别区分了 Agent 的最终回答和环境中的真实结果。例如，Agent 说“机票已经预订”，不代表数据库里真的存在订单。[Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

因此，第一优先级通常不是“每一步是否和设计稿完全一致”，而是“用户的任务是否真的完成”。

### 2.2 用四个问题判断优先级

可以从四个方面判断一个问题是否值得投入评测：

| 判断维度 | 要问的问题 | 优先级较高的信号 |
|---|---|---|
| 业务影响 | 出错会影响什么？ | 任务失败、用户损失、投诉、合规或资金风险 |
| 发生概率 | 这个问题多常见？ | 高频任务反复失败，或错误在多个场景中出现 |
| 不确定性 | 团队是否知道 Agent 能否稳定做好？ | 靠人工感觉判断、不同运行结果波动很大 |
| 可改进性 | 测出问题后能否采取行动？ | 可以调整提示词、上下文、工具、权限或流程 |

可以把它理解成一个简化的产品判断：

```text
评测优先级 ≈ 业务影响 × 发生概率 × 不确定性 × 可改进性
```

对于资金、安全、隐私和合规等高风险环节，即使发生频率不高，也应提高优先级；近期频繁修改的环节也更需要回归评测。对于影响很小、已经稳定，而且短期不会修改的环节，可以暂缓专项评测。

### 2.3 从三层结果中选择评测点

Agent 的评测对象可以分成三层：

| 层级 | 主要问题 | 示例 |
|---|---|---|
| 最终结果 | 用户目标是否真正完成 | 是否正确判断可退货，退款单是否真实创建 |
| 关键过程 | 是否在重要节点做对了决定 | 是否查询正确订单，是否使用有效规则，是否在高风险情况下转人工 |
| 运行约束 | 完成任务的代价和风险是否可接受 | 是否超时，成本是否过高，是否越权，是否陷入循环 |

通常先评测最终结果，再评测会影响结果、安全、成本和可解释性的关键过程。

不要因为 Agent 存在十个步骤，就默认需要十套同等复杂的评测。很多情况下，只要确认最终环境状态正确，再对少数关键决策增加检查，就已经能够覆盖主要风险。

### 2.4 示例：电商客服 Agent 什么值得测

用户问：“我七天前签收的这件商品还能退吗？”

第一版可以优先检查：

- 是否找到了正确订单和签收时间。
- 是否使用了当前有效的退货规则。
- 是否根据商品类型和订单状态得出正确结论。
- 无法确认时，是否说明原因并转人工，而不是编造答案。
- 如果 Agent 执行了退款，退款单是否真的创建成功。

可以暂缓的内容包括：某个低频过渡语是否足够自然、两个都能完成任务的工具调用顺序是否完全一致，以及不影响用户理解的轻微措辞差异。

## 3. 如何进行 Agent 评测：三步方法论

### 3.1 第一步：目标和任务

评测前先说清楚 Agent 为什么存在，以及用户希望它完成什么任务。

可以按照下面的顺序拆解：

```text
产品目标
  → 用户任务
  → 成功结果
  → 关键失败
  → 评测任务
```

例如：

| 项目 | 退货咨询示例 |
|---|---|
| 产品目标 | 提高常见售后问题的自助解决率，同时减少错误承诺 |
| 用户任务 | 判断一笔订单是否符合退货条件 |
| 成功结果 | 给出正确结论和依据；需要执行时，真实完成操作 |
| 关键失败 | 用错订单、引用过期规则、错误承诺、越权退款、该转人工时没有转 |
| 评测任务 | 提供订单、商品和规则环境，让 Agent 完成判断或操作 |

一条合格的评测任务，至少要包含：

- **输入**：用户请求，以及 Agent 在真实使用中能获得的信息。
- **环境**：可调用的工具、数据状态、权限和必要约束。
- **成功标准**：什么结果算完成，哪些错误不能接受。
- **检查对象**：最终输出、环境状态，以及确有必要检查的关键步骤。

任务描述要足够清楚。如果两位熟悉业务的人无法对“是否通过”形成基本一致的判断，说明任务或标准还需要继续澄清。每类重要任务最好准备一个确定可以通过评测的参考结果，用来验证题目和评测器本身没有问题。[Anthropic：从 0 到 1 建立 Agent 评测](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### 3.2 第二步：指标和数据 / 用例

#### 3.2.1 选择指标

指标要跟任务目标对应，不要一开始就堆很多分数。

| 评测维度 | 可以使用的指标 | 适用问题 |
|---|---|---|
| 任务结果 | 任务成功率、正确率、真实操作完成率 | Agent 是否完成用户目标 |
| 回答质量 | 正确性、完整性、有依据程度、表达清晰度 | 最终回答是否可信、可用 |
| 工具使用 | 工具选择正确率、参数正确率、结果处理正确率 | Agent 是否正确连接外部能力 |
| 安全与边界 | 越权率、危险操作拦截率、敏感信息泄露率 | Agent 是否在允许范围内行动 |
| 效率 | 总耗时、工具调用次数、Token 与单次任务成本 | 完成任务的代价是否合理 |
| 稳定性 | 多次运行成功率、失败波动、异常终止率 | Agent 能否持续稳定地完成任务 |

一个任务可以有多个指标，但要区分主指标和约束指标。例如，退货咨询的主指标是判断正确率；不能出现越权退款是安全约束；耗时和成本则是效率约束。

不要把所有指标简单加权成一个总分后就停止分析。总分可以用于快速比较版本，但具体改什么，仍然需要回到单项分数、失败类型和执行链路。

#### 3.2.2 建立测试用例

第一批用例可以来自：

- 产品需求中明确要求支持的典型任务。
- 团队每次发布前都会手动检查的场景。
- 线上用户反馈、失败记录和人工接管案例。
- 低频但损失较大的安全、资金或合规场景。
- 容易混淆的相似情况，以及“应该做”和“不应该做”的对照案例。

起步阶段不一定需要几百条数据。Anthropic 的实践建议是，可以先从 20～50 条来自真实失败和人工测试的简单任务开始，再随着产品成熟扩充覆盖范围。这个数量不是硬标准，重点是用例具有代表性，并能帮助团队做出决策。[Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

可以把用例集分成三组：

| 用例集 | 内容 | 用途 |
|---|---|---|
| 核心任务集 | 高频、代表性的主要任务 | 比较整体能力，建立版本基线 |
| 回归集 | 曾经出错并已经修复的案例 | 防止旧问题再次出现 |
| 风险与边界集 | 高风险、异常输入、工具失败、权限限制 | 验证安全边界与异常处理 |

每条用例还可以标记任务类型、难度、风险等级、数据来源和首次出现版本，方便按问题类别查看结果。

一份简化的用例可以这样写：

```text
用例名称：签收第 7 天的普通商品退货咨询
用户输入：这件商品还能退吗？
环境状态：订单已签收 7 天；商品不属于特殊品类；规则版本为 v3
期望结果：可以申请退货；说明截止条件；不承诺立即退款
必须检查：订单查询正确、规则版本正确、最终结论正确
禁止行为：编造订单状态、直接创建退款、引用旧规则
```

#### 3.2.3 同时使用离线评测和线上信号

- **离线评测**：在上线前，用固定数据集比较不同模型、提示词或流程，适合基线测试和回归测试。
- **线上评测**：对真实运行数据进行抽样打分、用户反馈分析和异常监控，适合发现测试集没有覆盖的新问题。

离线评测可重复、便于版本比较，但可能与真实用户分布脱节；线上数据更真实，但通常缺少标准答案，而且问题已经发生在用户面前。两者应该互相补充：线上问题进入离线回归集，离线改进上线后继续接受真实流量检验。[LangSmith：Evaluation types](https://docs.langchain.com/langsmith/evaluation-types)

### 3.3 第三步：方法和工具

“人工测试”和“自动化测试”描述的是评测由谁、以什么方式执行；代码规则、LLM-as-a-Judge 和 Agent-as-a-Judge，则是几种不同的自动评分方法。实际项目通常会组合使用。

#### 3.3.1 人工测试

由产品经理、测试人员、业务专家或真实用户体验 Agent，并根据标准给出判断。

**适合：**

- 评测体系刚建立，还不知道什么算好。
- 任务涉及专业判断、用户体验或复杂业务语境。
- 需要发现意料之外的问题。
- 需要校准自动评测器。

**局限：** 速度慢、成本高，不同评测人可能标准不一致，也不适合每次代码变更都全量执行。

人工评测不是自动评测建立后就可以取消的步骤。OpenAI 建议由领域专家定期检查 LLM 评测器是否与人工判断一致，并直接抽查系统日志。[OpenAI：How evals drive the next chapter in AI for businesses](https://openai.com/index/evals-drive-next-chapter-of-ai/)

#### 3.3.2 基于规则或代码的自动化测试

用确定性的规则检查结果，例如：

- JSON 是否符合结构要求。
- 工具名称和参数是否合法。
- 数据库中是否真实创建了退款单。
- 是否访问了禁止访问的数据。
- 总耗时、调用次数和成本是否超过阈值。

**优点：** 速度快、便宜、结果稳定，适合持续集成和大规模回归。

**局限：** 只能检查已经明确写成规则的内容，难以判断表达是否清楚、理由是否充分等开放问题。

如果一个结果可以直接用程序验证，优先使用代码，而不是让另一个模型猜。例如，判断退款是否成功，最好查询真实环境状态，而不是只让模型阅读 Agent 的文字回复。

#### 3.3.3 LLM-as-a-Judge

让一个大模型根据评分标准，对 Agent 的回答或执行记录进行打分。

适合判断：

- 回答是否完整、清晰、有帮助。
- 是否依据给定材料作答。
- 是否遵循业务规则和沟通要求。
- 两个版本中哪一个更好。

一份可靠的 Judge 提示词应包含明确的评分对象、评分维度、各等级定义、必要证据，以及信息不足时可以返回“无法判断”。复杂任务可以拆成多个维度分别评测，不要让一个 Judge 同时凭感觉给出所有分数。

LLM Judge 能提高评测规模，但它也可能受到表述风格、答案顺序、模型偏好和含糊标准影响。正式使用前，需要用一组人工标注样本检查它与业务专家判断的一致性，之后也要持续抽查。

#### 3.3.4 Agent-as-a-Judge

LLM-as-a-Judge 通常读取已经提供的输入、输出或执行记录；Agent-as-a-Judge 则拥有自己的工具和任务循环，可以主动寻找证据，再做判断。

例如，评测一个研究 Agent 时，Judge Agent 可以打开引用来源，检查原文是否支持结论；评测一个操作型 Agent 时，它可以查询数据库、查看页面状态或读取任务产物，确认动作是否真实完成。

Agent-as-a-Judge 更适合：

- 证据分散在多个文件、网页、数据库或执行步骤中。
- 只看最终回答无法确认任务是否完成。
- 需要检查复杂产物或完整执行轨迹。

但它不是“更高级，所以一定更好”。Judge Agent 自己也可能选错工具、漏看证据或产生新的不确定性，而且评测成本与耗时更高。Agent-as-a-Judge 仍是持续发展的方法，适合在复杂任务中作为代码检查、LLM Judge 和人工复核的补充，而不是未经校准就充当唯一标准。[Agent-as-a-Judge 论文](https://arxiv.org/abs/2410.10934)、[AJ-Bench：环境感知的 Agent-as-a-Judge 评测](https://arxiv.org/abs/2604.18240)

#### 3.3.5 如何组合评测方法

可以遵循一个简单原则：**优先使用成本最低、能够可靠判断问题的方法。**

| 要判断的内容 | 优先方法 |
|---|---|
| 格式、字段、阈值、数据库状态 | 代码或规则 |
| 表达质量、语义正确性、是否有依据 | LLM-as-a-Judge + 人工校准 |
| 需要主动访问环境才能获得证据 | Agent-as-a-Judge + 确定性检查 |
| 高风险、标准尚不清楚或存在争议 | 业务专家人工评测 |

一条用例可以同时拥有多个评测器。例如，退款任务可以用代码检查退款单状态，用 LLM Judge 检查对用户的解释，再由人工抽查高风险失败案例。

### 3.4 一些 Agent 评测平台和产品

平台可以帮助管理数据集、运行实验、保存分数和比较版本，但平台不能替代业务目标、指标和用例设计。

| 平台 / 工具 | 适合的使用方式 | 主要特点 |
|---|---|---|
| [LangSmith](https://docs.langchain.com/langsmith/evaluation-types) | 希望把 Trace、数据集、实验、离线与线上评测放在一起 | 支持代码评测器、LLM-as-a-Judge、成对比较、人工标注等方式 |
| [Langfuse](https://langfuse.com/docs/evaluation/core-concepts) | 重视可观测性与评测联动，并希望保留云服务或自托管选择 | 支持人工分数、代码评测器、LLM Judge、数据集实验和线上规则 |
| [Arize Phoenix](https://arize.com/docs/phoenix/evaluation/evals) | 希望使用开源方案完成 Trace 分析、数据集实验和评测 | 支持代码评测、LLM Judge、人工标签和 OpenTelemetry / OpenInference 接入 |
| [Braintrust](https://www.braintrust.dev/docs/evaluate) | 希望管理实验、评分器、CI 回归和线上质量监控 | 支持数据集、实验快照、代码或模型评分器，以及线上评分 |
| [Promptfoo](https://www.promptfoo.dev/docs/configuration/expected-outputs/) | 偏好配置文件和命令行，希望在本地或 CI 中比较模型与 Agent | 支持规则断言、模型评分、工具调用与 Agent 轨迹检查 |

选型时需要比较：现有技术栈、是否需要自托管、数据是否可以上传、团队是否需要界面化标注、是否要接入 CI，以及调用与存储成本。工具能力变化较快，正式采用前应再核对当前版本、部署方式和价格。

## 4. Agent 评测的注意事项

### 4.1 评测的是整个 Agent 系统，不只是模型

Agent 的结果同时受到模型、提示词、上下文、知识库、记忆、工具、权限、编排逻辑和外部环境影响。

换了模型以后分数提高，不代表问题一定来自旧模型；模型可能只是更好地绕过了一个工具设计缺陷。评测结果需要结合执行链路做原因分析，避免把所有问题都归为“模型不够强”。

### 4.2 不要把 Agent 自己说“完成了”当成成功

对于会修改外部状态的任务，要检查真实结果。例如：

- 邮件是否发给了正确的人。
- 日历事件是否真实创建。
- 数据库记录是否正确更新。
- 文件是否存在于指定位置并符合要求。

最终回答可以作为证据之一，但不能替代环境状态。

### 4.3 结果优先，但关键过程也不能完全忽略

如果有多条合理路径可以完成任务，就不应强制 Agent 必须按照唯一工具顺序执行。过度固定执行路径，会把有效但不同的方案误判为失败。

但以下过程仍值得检查：

- 是否越权或绕过审批。
- 是否使用了错误的数据源。
- 是否泄露敏感信息。
- 是否出现无效循环和异常成本。
- 业务明确要求必须执行的步骤是否完成。

原则是：**不要为了控制 Agent 而检查所有路径，只检查会影响结果、风险和成本的关键路径。**

### 4.4 Agent 具有随机性，一次通过不代表稳定

同一个任务重复运行，Agent 可能走不同路径并得到不同结果。重要用例应进行多次测试，至少同时观察：

- **首次成功能力**：第一次运行是否成功。
- **多次稳定性**：重复运行时是否持续成功。
- **失败分布**：失败集中在哪些任务和步骤。

Anthropic 用 pass@k 表示多次尝试中至少成功一次的概率，用 pass^k 表示多次尝试全部成功的概率。对于允许多次尝试的探索任务，可以关注前者；对于客服、支付等要求每次都可靠的场景，更需要关注后者所体现的稳定性。[Anthropic：Agent 评测中的非确定性](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### 4.5 先评测评测器

自动评测器也会犯错。上线使用前，需要验证：

- 参考答案能否通过。
- 明显错误的答案能否被识别。
- 两位业务专家认可的结果，Judge 是否基本一致。
- 改变答案顺序或表达风格后，评分是否出现无关偏差。
- 信息不足时，Judge 是否愿意返回“无法判断”。

还要定期阅读评测失败的完整执行记录，确认低分来自 Agent 的真实问题，而不是题目歧义、环境故障或评分规则错误。

### 4.6 用例要平衡，避免把 Agent 优化到另一个极端

只测试“应该调用搜索”的情况，可能得到一个遇到任何问题都搜索的 Agent；只测试“应该转人工”的高风险案例，可能让 Agent 变得过度保守。

评测集应该同时包含：

- 应该做与不应该做。
- 正常情况与异常情况。
- 容易任务与困难任务。
- 高频任务与低频高风险任务。

### 4.7 不要在测试集上反复调到满分

如果团队根据同一批测试用例不断修改提示词，Agent 可能只是适应了这些题目，并没有真正提高真实表现。

可以保留一部分不参与日常调试的验证集；上线后继续用新流量检查效果，并定期把新的真实失败补充进回归集。评测集达到接近满分时，也要增加更困难、更接近真实使用的新任务，而不是继续用已经饱和的分数证明系统进步。

### 4.8 不要让单一分数掩盖关键风险

如果 99 个普通问题回答正确，但 1 个高风险退款任务越权执行，平均 99 分仍然不能代表可以上线。

对于越权、数据泄露、错误付款等严重失败，可以设置为必须通过的门槛，而不是与普通表达分数相互抵消。

同时警惕为了提高指标而产生的“投机行为”：例如只写得更长来提高完整性评分，或者通过修改测试条件让自己更容易通过。指标必须持续回到真实用户目标和业务结果上。

### 4.9 控制数据、环境与版本

要记录模型、提示词、工具、知识库、评测器和数据集版本。不同版本的评测应尽量运行在一致、隔离的环境中，避免缓存、残留文件、共享状态和外部服务波动干扰结果。

测试数据和执行记录还可能包含用户信息、内部文档和业务数据。应进行脱敏、权限控制和保留期限管理，不要为了评测方便复制不必要的敏感数据。

## 5. 如何搭建第一版评测飞轮

不需要等 Agent 完全开发完成再开始评测。第一版可以按下面的顺序搭建：

1. **选择任务**：选出 3～5 类最重要的用户任务。
2. **跑通流程**：用少量真实或接近真实的案例完成人工测试。
3. **定位问题**：结合 Trace 找到影响任务结果的主要失败点。
4. **确定指标**：每类任务设置一个主指标，再补充安全、成本或延迟约束。
5. **建立用例集**：收集 20～50 条代表性用例，包含正常、异常和高风险情况。
6. **组合评测器**：能用代码确定的先用代码，开放质量使用 LLM Judge，高风险和争议案例保留人工复核。
7. **建立基线**：记录当前版本的结果，而不是一开始就追求高分。
8. **一次解决一类问题**：先针对最有价值的失败点修改 Agent。
9. **运行回归**：既测试专项问题，也测试核心任务集，避免局部改善造成整体退化。
10. **上线继续观察**：把新的真实失败加入回归集，进入下一轮迭代。

以退货咨询为例：

```text
线上发现 Agent 经常引用过期退货规则
  → 将相关失败按商品类型和订单状态分类
  → 选出影响最大的典型案例
  → 增加“规则版本正确率”和回归用例
  → 修改检索过滤与规则版本管理
  → 重跑专项用例和核心任务集
  → 确认正确率提高，且耗时、成本、转人工率没有异常退化
  → 上线后继续观察真实退货咨询
```

这就是评测飞轮：**不是一次性做一份测试报告，而是不断把问题变成用例，把用例变成改进证据。**
