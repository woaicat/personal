# 实战演练：从 0 到 1 设计一个 B2B 销售助手 Agent

前面我们已经学习了 Agent 设计的主要知识，包括需求调研、模型选择、系统提示词、工具设计、上下文管理、人机协作和评测等。

但在实际工作中，我们很少按照课程目录，一项接一项地完成设计。
面对一个业务需求，首先需要弄清楚用户遇到了什么问题、希望如何解决，再根据具体情况决定需要哪些 Agent 能力，以及如何实现这些能力。

真实的设计过程通常围绕一个个需要解决的问题展开。例如，为什么这个需求需要 Agent？使用普通工作流能不能解决？Agent 应该自主完成哪些任务？哪些操作必须受到程序或人工控制？每一项技术决策都需要结合实际需求、资源和限制进行判断。

最终我们的目标是学会一种可迁移的 Agent 设计方法：如何从一个尚未明确的业务需求出发，通过分析、判断和取舍，逐步形成一个合理、完整、可落地的 Agent 产品方案。

这一课，通过一个具体案例，把前面学习的知识应用到实际的产品设计中。从最初的业务需求出发，逐步确定产品方案和技术方案，最终整理出一份可以交给开发团队讨论和实施的需求说明文档。

本课选择的案例是 **B2B 销售助手 Agent**。需求来自企业销售团队在客户研究和开发资料准备过程中遇到的实际问题，后续为了说明设计方法而补充的企业信息、客户资料和部分项目条件属于教学模拟设定。

## 1、需求和背景

### 1.1 了解业务背景

某 B2B 软件公司主要面向企业客户提供 AI 软件产品和技术服务，包括企业知识助手、智能客服及业务流程自动化等解决方案。

公司销售团队需要主动寻找潜在客户，并通过微信、电话、邮件等方式建立联系，争取进一步沟通和合作的机会。

在正式接触客户之前，销售人员通常需要了解客户公司的主营业务、组织情况、近期发展动态，以及可能存在的产品需求，再根据这些信息准备个性化的销售开发资料。

但实际工作中，客户信息分散在 CRM 系统、企业官网和互联网中，人工收集和整理需要花费大量时间。销售人员不仅要查找资料，还需要从这些信息中判断客户可能面临哪些业务问题，以及公司的产品能否提供帮助。

为了提高销售团队的工作效率，公司计划开发一个 AI Agent。当 CRM 中出现一条新的有效线索，并且已经分配给某位销售人员时，Agent 能够自动开展客户研究、分析潜在需求，并生成相应的开发资料和跟进建议。

此外，销售人员还希望能够随时与 Agent 对话。例如，询问某家客户的最新业务动态、讨论跟进策略，或者查询公司产品是否支持客户提出的某项功能。

以上就是我们最初得到的业务需求。

### 1.2 分析用户和现有工作流程

拿到需求后，我们首先需要了解产品的使用者，以及他们目前是如何完成相关工作的。

本案例的主要用户是一线销售人员。销售主管也关心客户开发效率和销售结果，但首版产品主要服务于销售人员日常的客户研究和开发准备工作，因此暂时不设计主管管理工作台。

接下来，我们梳理销售人员收到一条新线索后，通常需要完成哪些工作。

**第一步，了解线索和客户。** 销售人员查看 CRM 中的企业名称、所属行业、线索来源、联系人和历史沟通记录，判断目前已经掌握哪些信息，以及客户是否有过明确的产品咨询。

**第二步，开展客户研究。** 通过企业官网、新闻和其他公开资料，了解客户的主营业务、产品服务、组织情况、近期发展动态，以及可能与公司产品相关的信息。

**第三步，分析潜在需求。** 结合客户的业务特点和近期动态，判断客户可能面临哪些问题，进一步考虑公司的软件产品能够提供哪些帮助。

**第四步，准备客户开发资料。** 根据已有信息，准备适合的微信沟通话术、电话沟通提纲、产品介绍或其他开发资料，确定首次接触时应该重点介绍什么。

**第五步，制定跟进策略。** 分析客户内部可能参与产品采购决策的部门和岗位，寻找值得优先联系的对象，并根据后续沟通情况调整策略。

这些工作之间存在紧密联系。例如，销售人员发现一家零售企业正在拓展门店，可能会进一步研究其门店运营和员工培训体系，再判断企业知识助手是否具有潜在应用价值。如果 CRM 中已经记录过客户曾咨询过相关产品，那么分析的重点又应该有所不同。

我们希望 Agent 能够综合内部和外部信息开展研究，减少销售人员反复查找和整理资料的工作，并为下一步客户沟通提供更有针对性的建议。

### 1.3 明确任务如何触发

在梳理用户工作流程时，我们发现一个需要提前明确的问题：Agent 应该在什么时候开始工作？

按照最初的需求，销售人员不需要每次手动打开 Agent，输入客户名称，再要求它开展研究。公司希望在 CRM 收到有效线索并完成销售分配之后，由系统自动触发研究任务。

因此，我们需要先明确什么叫有效线索，以及如何避免不必要的任务执行。

CRM 中可能存在刚刚录入、尚未审核的线索，也可能存在缺少企业信息、被标记为无效或者已经进入后续销售阶段的线索。如果所有线索都自动触发 Agent，可能造成大量无效搜索和模型调用。

考虑到 CRM 本身已经具有线索状态和负责人管理能力，我们决定复用现有业务规则，由 CRM 负责判断线索是否有效，Agent 不再重复建设一套线索评分系统。

需要同时满足以下条件，才会自动创建研究任务：

- 线索状态为有效。
- 线索已经分配给具体销售人员。
- 线索包含可识别的企业名称或其他有效企业标识。
- 当前线索尚未创建相同类型的自动研究任务。

当 CRM 满足这些条件时，向 Agent 服务发送一条任务触发事件。Agent 根据线索 ID 获取相应客户信息，开始后续研究。

这里还需要考虑重复事件的问题。比如 CRM 因为网络问题重复发送通知，不应该导致 Agent 反复研究同一家企业，因此需要在程序层面实现任务去重。

另外，CRM 中的客户名称也可能不完整或存在重名。Agent 在进行外部搜索时，需要根据官网域名、企业所在地、主营业务等信息确认目标企业。如果无法可靠判断，应当停止使用身份不确定的外部资料，并请求销售人员确认。

### 1.4 判断是否需要 Agent

理解了用户需求和工作流程后，我们还需要考虑采用什么技术方案解决这些问题。

一种比较简单的方法是开发传统的 CRM 扩展功能，例如自动获取线索信息，并调用固定接口查询企业资料，再根据预设模板生成客户报告。这种方式实现比较直接，流程容易控制，但能够处理的信息和场景通常受到事先编排的限制。

另一种方法是搭建 AI 工作流，提前设置数据查询、需求分析、产品匹配和资料生成等步骤，让模型按照固定流程完成任务。对于信息来源和处理步骤相对稳定的场景，这种方案已经能够解决很多问题。

但我们的需求还存在一定的不确定性。

不同企业的公开信息差异很大，有些客户官网内容丰富，有些企业的信息分散在新闻、招聘和行业资料中。Agent 可能需要根据首次搜索结果调整研究方向，或者判断某些信息已经足够、无需继续搜索。

例如，在研究一家零售企业时，系统发现该企业近期正在快速扩张门店，就可能进一步查找其门店管理和员工培训信息。而研究一家软件公司时，系统可能更需要关注其产品技术路线和业务合作动态。

此外，销售人员提出的问题也具有很大的灵活性。他们可能要求 Agent 重新研究某个业务方向、解释某项判断依据、比较不同产品方案，或者只修改一份开发资料中的某段内容。

这些需求适合使用能够自主选择行动和调用工具的 Agent。

因此，我们决定采用**固定业务规则 + Agent** 的设计方式。

CRM 负责线索判断、任务触发、用户权限和结果展示；Agent 负责根据当前客户情况自主选择信息来源、开展研究、分析潜在需求、生成开发资料、回答销售人员问题等。

这样既能复用原有 CRM 的确定性业务逻辑，也能让 Agent 灵活处理不同客户的研究任务。

### 1.5 明确产品目标、范围和限制

经过分析，我们可以将产品目标确定为：

**设计一个嵌入 CRM 的 B2B 销售助手 Agent。当有效线索被分配给销售人员后，Agent 自动整合 CRM、互联网和内部产品知识，生成客户研究报告、潜在需求分析、开发资料及跟进建议，并支持销售人员通过对话持续讨论和修改。**

为了控制第一版产品的复杂度，我们确定以下范围和限制。

- **业务范围：** 只支持单个客户的研究和资料生成，不考虑批量客户处理。
- **用户范围：** 主要面向线索负责人，不设计多人协同研究和管理功能。
- **数据来源：** CRM 使用模拟数据，外部信息通过网络搜索工具获取，内部产品信息来自授权产品资料。
- **交付内容：** 客户调研报告、潜在需求分析、开发资料草稿和客户跟进建议。
- **交互方式：** 在现有 CRM 客户详情页中嵌入对话式 Agent 工作区。
- **操作边界：** 不自动发送邮件或企业微信消息，不修改 CRM 客户资料、线索状态或跟进记录。

还有一项重要要求：Agent 的研究结论必须区分事实和推断。它可以根据公开信息提出潜在需求假设，但不能把客户业务动态直接解释成明确的采购意向，更不能编造企业事实、联系人或产品能力。

## 2、设计产品方案

经过需求分析，我们已经明确了 Agent 的目标和基本能力。接下来，通过一个具体的客户研究场景，进一步设计产品的工作流程、交付内容及人机协作方式。

### 2.1 从一个具体客户开始

假设销售团队正在开发一家连锁零售企业，CRM 中新增了一条有效线索，并已分配给销售人员 A。

线索信息如下：

| 字段     | 模拟数据        |
| ------ | ----------- |
| 线索 ID  | L-1024      |
| 企业名称   | 澄远零售（虚构企业）  |
| 所属行业   | 连锁零售        |
| 线索状态   | 有效          |
| 销售负责人  | 销售人员 A      |
| 企业官网   | 已录入         |
| 历史沟通   | 曾初步了解企业知识助手 |
| 当前采购意向 | 尚未确认        |

假设外部公开资料中还能够查询到，这家企业近期正在拓展新的区域门店，并发布了门店运营相关岗位的招聘信息。这些外部信息属于模拟材料，实际产品需要通过网络搜索工具获取并核实。

当 CRM 将这条线索分配给销售人员 A 后，系统自动创建 Agent 研究任务。

### 2.2 自动收集客户情报

收到任务后，Agent 首先需要读取 CRM 中的线索资料，确认目标企业及已有的内部信息，然后根据研究需要开展互联网搜索。

内部 CRM 主要提供线索来源、企业基本信息、已有联系人和历史沟通记录。外部搜索则重点补充主营业务、产品服务、业务布局、近期发展动态及公开组织信息。

搜索过程中，Agent 需要判断哪些内容真正属于目标企业，以及是否足够可靠。例如，企业官网可以帮助确认主营业务，近期招聘信息可以反映企业正在关注哪些业务方向，但较早的新闻不能直接代表当前经营情况。

另外，也不应该让 Agent 无限制地搜索。它需要根据研究目标判断什么时候已经获得足够的信息，什么时候值得进一步查找，以及什么时候应该承认公开资料不足。

最终，Agent 生成一份简洁的客户调研报告，重点包括企业概况、主营业务、近期动态、CRM 已有沟通情况和主要研究发现。

对于重要信息，应当保留来源和时间。例如，企业主营业务来自官网的哪一个页面，近期动态是哪一天发布的新闻，历史沟通来自 CRM 中的哪条记录。

这样，销售人员不仅能够看到 Agent 整理的结论，还可以在需要时回到原始资料进行核实。

### 2.3 分析客户潜在需求

完成客户信息收集后，Agent 还需要根据这些资料分析可能的销售机会。

继续使用澄远零售这个例子。假设 Agent 发现该企业正在拓展新的区域门店，并且在 CRM 历史沟通记录中了解到，客户曾提到门店员工培训资料管理比较分散。

根据这些信息，Agent 可以提出一个初步判断：随着门店数量增加，企业可能面临知识资料维护、门店员工培训和日常业务答疑等问题。

接下来，它需要查找公司现有的软件产品，判断是否有能够解决这些问题的产品或方案。

假设内部产品资料显示，公司提供的企业知识助手支持文档检索、来源引用和权限控制，那么 Agent 就可以建立初步的客户需求与产品能力匹配关系。

| 分析内容     | 案例结果                      |
| -------- | ------------------------- |
| 客户业务动态   | 正在拓展区域门店                  |
| CRM 已有信息 | 曾提及门店培训资料管理分散             |
| 潜在业务问题   | 多门店知识更新、员工培训和日常答疑可能存在效率问题 |
| 可匹配产品    | 企业知识助手                    |
| 可能提供的价值  | 帮助员工查询授权知识、获取资料和业务操作指引    |
| 需要进一步确认  | 是否已有相关系统、当前使用范围、是否存在升级计划  |

这里最重要的是区分**已经确认的客户事实、基于事实提出的需求假设，以及公司真正具备的产品能力**。

Agent 不能因为客户正在扩张门店，就断言客户已经决定采购知识管理系统。同样，如果公司产品目前不具备某项功能，也不能为了让销售方案看起来更有吸引力而自行补充。

最终，Agent 应当生成一份个性化的需求分析报告，列出潜在需求、判断依据、匹配产品和待确认问题，供销售人员进一步判断。

### 2.4 生成客户开发资料

有了客户研究报告和潜在需求分析后，Agent 可以进一步帮助销售人员准备开发资料。

考虑到国内 B2B 销售的实际习惯，我们不把邮件作为唯一或默认交付形式。首版优先支持微信沟通话术、电话沟通提纲和简短的产品方案介绍，销售人员也可以要求生成邮件等其他形式。

例如，针对澄远零售，Agent 可以生成以下微信沟通草稿：

> 您好，了解到贵司近期正在拓展区域门店，想和您交流一下多门店知识管理方面的经验。我们主要为企业提供 AI 知识助手，可以帮助员工查询业务资料、获取操作指引，并按照权限使用相关知识。如果贵司也在关注门店培训和知识管理效率，想了解一下是否方便安排一次简单交流。

这只是一份初稿。Agent 应当让开发资料与实际客户特点相关联，并确保使用的客户事实、产品功能和案例信息都有可靠依据。

同时，CRM 的内部沟通记录可以用于帮助销售人员判断客户需求，但其中尚未公开的客户信息不应该被直接写进对外话术。

销售人员可以通过对话继续修改。例如，要求“语气更自然一点”“不要一开始就介绍产品，先讨论客户的业务情况”，或者“分别生成面向 IT 负责人和运营负责人的沟通版本”。

Agent 应当根据这些要求进行局部修改，保留已经确认的信息，不必重新开展整个研究任务。

### 2.5 推荐客户跟进对象和策略

除了开发资料，销售人员还希望知道应该优先联系谁，以及下一步如何开展沟通。

因此，我们可以让 Agent 根据客户业务特点、组织信息和公开活动，推荐值得关注的部门、岗位或人员。

例如，澄远零售的门店知识管理需求可能同时涉及运营部门和信息化部门。运营负责人更可能了解业务流程和员工培训问题，信息化负责人则可能关心系统集成、数据安全和技术实施。

Agent 可以根据这些信息，建议优先联系哪些角色，并说明选择原因。如果公开资料中能够确认相关人员近期参与了行业活动、发布了业务观点或负责相应工作，也可以将这些信息作为推荐依据。

但这里需要注意，公开活跃度不等于实际采购意愿，也无法单独证明某个人具有采购决策权。对于没有足够证据的情况，Agent 应当优先推荐岗位或部门，而不是编造具体联系人。

最终的跟进建议需要回答三个问题：应该优先接触谁或什么角色，为什么推荐这个对象，以及首次沟通中应该重点确认哪些问题。

此外，销售人员还可以通过对话和 Agent 讨论跟进方案。例如，询问“如果客户已经有知识管理系统，我们应该怎样介绍产品优势”，或者“运营负责人对这个话题不感兴趣，下一步可以怎么沟通”。

这类问题需要结合当前客户研究结果和公司产品资料进行回答，而不应只生成一套通用销售话术。

### 2.6 提供公司产品信息问答

销售人员在日常工作中，还需要随时了解公司产品和解决方案。

例如，客户可能询问“你们的知识助手能否对接现有 OA 系统”“是否支持不同部门设置不同权限”“客户数据能否部署在本地”。

为了满足这类需求，Agent 需要能够查询公司正式的产品资料，并根据已有信息回答问题。

这项能力可以与客户研究结合使用，也可以独立运行。如果销售人员正在查看某个客户，Agent 可以结合客户的业务场景解释相关产品；如果用户只是询问产品功能，Agent 也应该能够直接回答，不要求先创建客户研究任务。

产品问答应当以公司审核通过的产品文档、功能说明和解决方案资料为依据。对于尚未明确的功能、价格、交付周期和技术承诺，Agent 应说明无法确认，并建议进一步联系对应的产品或技术负责人。

### 2.7 设计人机协作方式

目前我们已经确定，Agent 能够自动研究客户、分析潜在需求、生成开发资料和跟进建议。但在实际工作中，哪些事情可以交给 Agent 自主完成，哪些事情需要销售人员参与？

我们可以根据任务风险和用户实际工作需要进行划分。

**自动执行客户研究。** 当 CRM 线索满足触发条件后，Agent 可以自主调用已授权的只读工具完成研究。由于这个阶段不涉及真实对外沟通，也不会直接修改 CRM 业务数据，因此不需要销售人员逐步确认每次查询。

**提示关键不确定性。** 如果 Agent 无法确认企业身份、重要资料存在冲突，或者某项业务判断缺少依据，就应该明确告诉销售人员。对于影响研究对象识别的重大问题，需要等待人工确认后再继续。

**人工复核开发资料。** Agent 生成的沟通话术、产品介绍和跟进建议均作为草稿。销售人员可以查看来源、调整措辞、补充业务信息，并最终决定使用哪些内容。

**用户决定对外行动。** 首版不提供自动发送能力。实际联系客户、选择沟通渠道和决定后续销售动作，都由销售人员完成。

这种设计可以减少重复的人工操作，同时避免 Agent 在信息不完整的情况下替用户作出重要业务决定。

### 2.8 设计产品交互界面

根据前面的工作流程，我们决定将 Agent 直接嵌入 CRM 客户详情页，而不单独开发一个完整的客户管理平台。

可以把 Agent 工作区划分为三个主要部分。

**客户研究概览。** 展示 Agent 的研究状态、客户基本情况、主要业务动态和核心发现。研究完成后，销售人员可以展开查看详细报告及信息来源；研究失败或需要确认时，页面展示具体原因。

**交付物区域。** 分别展示客户调研报告、潜在需求分析、开发资料和跟进建议。用户可以查看、复制和编辑内容，也可以要求 Agent 修改某个部分。

**对话区域。** 销售人员可以围绕当前客户继续提问、讨论跟进策略、修改开发资料，也可以查询公司的产品知识。Agent 应当理解当前页面所关联的客户，并在需要时重新读取最新资料。

首版界面不需要复杂的可视化工作流。用户真正关心的是研究有没有完成、结论是否可信、资料能不能直接使用，以及遇到问题时能否继续与 Agent 讨论。

## 3、设计技术方案

完成产品设计后，我们需要考虑如何利用现有技术实现这些能力。这里重点介绍主要技术选择和设计依据，具体接口、提示词和运行参数可以在后续技术实现文档中进一步展开。

### 3.1 系统整体架构

根据前面的需求，我们可以将系统划分为四个主要部分。

**CRM 业务系统：** 负责有效线索判断、销售负责人分配、客户资料管理和 Agent 工作区展示。CRM 通过业务事件通知 Agent 服务创建任务。

**Agent 业务服务：** 负责接收线索事件、校验权限、创建和管理研究任务、保存交付物，并将执行状态和研究结果返回 CRM 页面。

**Agent 运行层：** 负责调用模型、选择工具、执行任务并根据工具返回结果继续行动。这部分使用成熟的 Agent Harness 实现，避免重新开发基础运行机制。

**工具与数据服务：** 提供 CRM 信息查询、互联网搜索、网页内容读取、产品知识查询和研究成果保存等能力。

一次完整的研究任务可以概括为：

**有效线索产生 → CRM 触发任务 → Agent 获取客户资料 → 自主搜索和分析 → 查询产品知识 → 生成研究成果 → CRM 页面展示 → 销售人员复核与修改**

其中，CRM 事件触发、权限校验、任务去重和结果保存由确定性程序负责。信息检索、研究方向选择、需求分析和内容生成则由 Agent 自主处理。

### 3.2 选择模型和 Agent Harness

首先，我们需要选择驱动 Agent 工作的大模型。

根据需求，这个任务主要依赖中文商业信息理解、多来源信息综合、信息可信度判断、产品能力匹配、文案生成和多轮工具调用等能力。

公开的模型评测可以帮助筛选候选模型，但最重要的仍然是在具体任务中验证。比如，可以准备几家不同行业的模拟客户，观察模型能否正确理解业务、识别潜在需求、调用工具，以及是否会编造产品能力和客户采购意向。

对于技术资源，我们假设公司已有内网模型服务，并且具备 Node.js / TypeScript 的后端开发能力。考虑到内部客户信息的安全要求，首版优先验证已有内网模型 DeepSeek-V4.1-Flash，是否采用还需要通过实际任务测试确定。

接下来选择 Agent Harness。

目前可以考虑 Pi coding agent SDK、Deep Agents 和 Agno 等开源框架。这些框架都可以用于构建具备工具调用能力的 Agent，但在开发语言、会话管理、自定义工具和运行控制等方面有所不同。

本案例选择 **Pi coding agent SDK**，主要基于以下考虑：

首先，Pi 已经提供 Agent Loop、模型调用、会话管理和上下文压缩等基础能力，可以减少重复开发。其次，它支持注册自定义工具，能够将 CRM、网页搜索和产品知识查询等业务能力提供给 Agent。最后，Pi 可以嵌入 TypeScript 服务，与本案例假设的后端技术环境比较匹配。

需要注意，Pi 只负责 Agent 的通用运行能力。CRM 数据查询、用户权限、产品知识服务和研究成果管理等业务功能，仍然需要由我们自行实现或封装。

### 3.3 设计工具

工具设计需要直接服务于前面确定的产品能力。

在本案例中，Agent 至少需要四类工具：CRM 数据查询、互联网搜索、产品知识查询和成果保存。

| 工具                         | 主要作用         | 使用场景          |
| -------------------------- | ------------ | ------------- |
| `get_lead`                 | 获取线索和企业基本资料  | 确认研究对象        |
| `get_crm_history`          | 获取历史沟通和已有联系人 | 了解客户已有需求      |
| `search_web`               | 搜索公开互联网信息    | 查询企业业务与动态     |
| `fetch_webpage`            | 读取指定网页内容     | 获取和核实来源       |
| `search_product_knowledge` | 检索内部产品资料     | 匹配产品能力、回答产品问题 |
| `get_artifact`             | 获取已有研究成果     | 后续对话和局部修改     |
| `save_artifact`            | 保存当前任务的研究成果  | 交付和更新草稿       |

其中，CRM 查询工具需要根据当前任务关联的线索和负责人进行权限校验，不能因为模型提供了某个客户 ID，就直接返回该客户的所有资料。

互联网搜索工具需要返回网页地址、标题、可用的发布时间和相关内容。对于能够进一步读取的网页，可以通过 `fetch_webpage` 获取正文，并保留来源信息供后续引用。

产品知识查询工具负责提供公司的正式产品资料。如果公司已有内部知识库，可以通过接口直接查询；如果资料规模较小，也可以先使用结构化数据或全文检索实现，不一定需要在首版建设复杂的 RAG 系统。

最后，研究成果保存工具负责将报告、分析和草稿与当前任务关联。Agent 通过这些工具读取和更新自己的研究成果，但不能直接修改 CRM 的销售业务数据。

### 3.4 设计 Agent Loop

Pi 已经提供 Agent Loop，因此我们不需要为每一次搜索、分析和内容生成都编写固定的执行节点。

当 CRM 触发任务后，Agent 首先获取线索信息，确认研究对象，然后根据客户特点选择需要查询的数据。每次工具返回结果后，模型可以判断当前信息是否足够，是否需要进一步搜索，以及下一步应该生成什么内容。

例如，Agent 在搜索一家连锁企业时，发现其正在拓展海外业务，可能继续寻找企业海外团队管理和服务体系相关的信息。如果后续资料不足，也可以停止这条研究方向，避免无限搜索。

我们需要为 Agent 设置明确的边界，例如单任务允许的工具调用预算、执行时间上限和异常处理规则，避免反复调用搜索工具却没有产生新的有效信息。

对于影响企业身份识别的重大问题，Agent 应暂停研究并请求用户确认。对于一般性的信息不足，可以生成有限的结果，并明确记录尚未确认的事项。

### 3.5 管理上下文和信息来源

这个 Agent 需要处理 CRM 历史记录、网页搜索结果、产品知识，以及销售人员的多轮对话，因此上下文管理比较重要。

可以直接复用 Pi 的会话管理和自动压缩能力，在上下文接近上限时对较早的历史进行摘要。同时，将完整研究成果和来源列表保存在任务存储中，让 Agent 按需读取，避免每轮都重新传入全部客户资料。

但我们还需要特别关注信息的时效性和来源。

CRM 中的历史沟通记录可能已经过期，网页搜索结果可能涉及同名企业，产品知识也可能出现版本更新。因此，关键事实应保留来源和获取时间。销售人员要求更新某个结论时，Agent 需要重新查询相关信息，而不能只依靠之前的会话摘要。

首版不需要建设跨客户长期记忆，也不自动共享不同客户任务中的内部沟通信息。

### 3.6 安全与权限控制

本案例需要读取 CRM 中的客户信息，还涉及互联网搜索，因此必须明确内部数据和外部工具之间的权限边界。

首先，CRM 查询工具需要校验当前任务的线索归属和用户权限。Agent 只能获取授权范围内的数据，不能直接操作 CRM 数据库。

其次，外部搜索结果和网页正文属于不可信输入。即使网页中包含要求 Agent 执行其他命令或访问内部系统的文字，也不能将这些内容当作系统指令。

另外，首版不向 Agent 提供企业微信发送、邮件发送或 CRM 修改工具，从工具层面限制其对真实客户和业务记录产生直接影响。

对于产品能力和客户事实，也需要进行输出检查。比如，开发资料中的产品功能必须能够关联到内部正式产品资料，重要客户动态必须存在可核实来源。

## 4、整理产品需求说明文档

经过前面的需求分析、产品设计和技术选择，我们已经能够整理出一份用于开发讨论的需求说明文档。

以下是本案例的简化版 PRD。

---

### 4.1 产品基本信息

**产品名称：** B2B 销售助手 Agent

**产品定位：** 嵌入现有 CRM 系统的 AI 销售助手，通过整合内部客户数据、外部公开信息和企业产品知识，辅助销售人员完成客户研究、潜在需求分析和开发资料准备。

**核心用户：** B2B 企业销售人员。

**产品目标：** 降低客户研究及资料准备的人工耗时，提高客户信息的可用性、潜在需求分析的质量和客户开发资料的针对性。

**需求范围：** 单客户自动研究、潜在需求分析、开发资料生成、跟进对象建议和产品信息问答。

**能力边界：** 不自动发送对外消息，不修改 CRM 业务数据，不进行批量客户研究，不自动判定客户具有明确采购意向。

### 4.2 核心业务流程

当 CRM 中一条线索首次满足有效、已分配负责人及企业信息完整等触发条件时，业务服务自动创建研究任务。

Agent 获取当前线索和历史沟通信息，开展外部公开资料搜索，并结合公司产品知识分析潜在需求。在确认信息来源和分析结果后，生成客户调研报告、需求分析、开发资料草稿及跟进建议。

研究完成后，CRM 客户详情页展示研究摘要和完整产物。销售人员可以查看来源、修改内容，或者通过对话继续讨论客户情况和跟进策略。

### 4.3 功能需求

| 编号  | 功能        | 需求说明                           |
| --- | --------- | ------------------------------ |
| F01 | 线索自动触发    | CRM 线索满足有效、已分配负责人等条件后，自动创建研究任务 |
| F02 | 任务去重与状态管理 | 重复事件不得创建重复任务，支持查看运行状态、异常和重试    |
| F03 | CRM 信息查询  | 读取当前任务授权的企业信息、已有联系人和历史沟通记录     |
| F04 | 公开信息搜索    | 自主查询企业主营业务、近期动态和公开组织信息，保留来源及时间 |
| F05 | 客户调研报告    | 整合客户概况、重要动态、CRM 历史和主要研究发现      |
| F06 | 潜在需求分析    | 根据已取得的信息提出需求假设，查询并匹配公司现有产品能力   |
| F07 | 客户开发资料    | 生成微信话术、电话提纲及产品介绍草稿，支持编辑和重新生成   |
| F08 | 跟进对象与策略建议 | 推荐相关岗位或可靠的公开人员信息，提供推荐依据和沟通建议   |
| F09 | 产品信息问答    | 根据正式产品资料回答功能、场景和技术限制等问题        |
| F10 | 多轮对话      | 支持围绕客户研究、产品能力和跟进方案继续讨论         |
| F11 | 来源与异常提示   | 展示重要信息依据，标明推断和待确认事项，提示工具或研究失败  |

### 4.4 交付物要求

首版为每条研究线索生成四类主要产物，所有产物都应关联当前 `lead_id` 和 `task_id`。

| 产物     | 内容要求                     | 展示方式  |
| ------ | ------------------------ | ----- |
| 客户调研报告 | 企业概况、主营业务、近期动态、CRM 历史、来源 | 结构化报告 |
| 潜在需求分析 | 潜在问题、判断依据、匹配产品、待确认问题     | 分析报告  |
| 客户开发资料 | 微信话术、电话提纲、产品介绍草稿         | 可编辑文本 |
| 跟进建议   | 推荐岗位或人员、选择依据、沟通问题        | 建议列表  |

此外，Agent 需要保存本次研究的重要来源信息，包括来源类型、标题、地址或记录 ID、时间及关联结论。

产品信息问答通过对话区提供，不要求每次客户研究都单独生成产品问答文件。

销售人员可以直接修改交付物，也可以通过对话要求 Agent 修改。用户修改过的内容应被保留，重新研究和自动更新不能未经提示覆盖人工编辑。

### 4.5 非功能需求

**安全性：** CRM 数据查询必须经过授权校验，不允许跨客户或跨用户访问内部沟通记录。Agent 不具备自动发送消息和修改 CRM 业务数据的权限。

**信息准确性：** 重要客户事实和产品能力应有可靠来源，潜在需求和联系人推荐应明确区分依据与推断。不能编造企业经营数据、产品能力、采购意向或具体联系人。

**可靠性：** CRM 重复事件、外部网络失败、企业身份歧义和任务中断时，系统应能够正确处理并保留已有成果。部分信息获取失败时，应当明确展示缺失范围，避免把不完整研究描述为完整结果。

**时效性：** 关键外部信息应记录发布时间和获取时间，内部产品问答应使用当前授权且有效的资料版本。

**可维护性：** 模型、提示词、工具和产品知识可以独立更新，并能够通过固定测试案例验证修改效果。

**可观测性：** 记录任务状态、重要工具调用、错误、耗时、模型版本和信息来源，支持后续问题定位。

### 4.6 验收标准

产品需要分别通过功能验收、业务质量验收和安全验收。

功能方面，验证有效线索能够正确创建任务，重复事件不会重复执行，Agent 可以读取授权 CRM 信息和公开资料，完成四类产物，并支持后续查询和修改。

业务质量方面，重点检查客户事实是否准确、主要结论是否有来源、需求分析是否合理、匹配产品是否真正具备相应能力，以及生成的开发资料是否具有针对性。

安全方面，跨客户越权读取、未经授权发送信息、泄露内部资料及编造关键产品能力都属于严重问题，应设置独立的验收限制，不能依靠其他指标的平均分通过。

---

以上就是首版需求说明文档的主要内容。实际开发时，还需要根据技术环境进一步补充 CRM 事件协议、工具接口字段、页面原型、任务状态和异常处理规则。

通过回顾前面的设计过程，我们可以发现，文档中的主要能力都能够对应到具体业务需求。例如，自动触发来自 CRM 线索处理流程，来源追溯来自客户研究的可信度要求，局部修改来自销售人员持续调整开发资料的工作方式。

如果一项功能无法说明自己要解决什么问题，就需要重新评估它是否应该出现在首版产品中。

## 5、验证我们的设计

完成需求说明文档后，我们还需要考虑如何判断这个 Agent 是否真正满足销售人员的需求。

对于 AI 产品，仅检查功能能否运行是不够的。Agent 可能成功调用所有工具、生成完整报告，但使用了错误的企业信息，或者基于薄弱证据提出不合理的客户需求判断。

因此，我们需要同时关注 Agent 自身的任务表现，以及产品上线后对销售工作的实际帮助。

### 5.1 确定评测目标

**Agent 的任务表现。** 重点关注研究任务成功率、客户关键信息准确率、重要结论的来源可追溯率、产品能力描述准确性，以及生成资料是否满足基本要求。

**业务效率。** 关注使用 Agent 前后，销售人员完成一份客户研究和开发资料准备所需的时间。除了 Agent 自动生成的耗时，还应该把人工核对和修改时间考虑进去，避免只衡量生成速度。

**用户使用情况。** 关注销售人员是否查看研究报告、是否使用或修改开发资料，以及是否通过对话继续讨论客户问题。还可以收集销售人员对报告准确性、建议实用性和资料针对性的评价。

**安全与可靠性。** 重点检查是否存在错误关联企业、越权获取客户信息、编造关键事实或产品能力，以及用户修改内容丢失等问题。

对于是否带来更多销售机会，可以作为后续观察指标。但实际销售结果受到客户质量、销售能力和沟通渠道等因素影响，不能直接把销售转化率的变化全部归因于 Agent。

### 5.2 构建测试数据集

我们可以准备一组模拟 CRM 线索，覆盖不同行业、不同信息完整程度以及不同历史沟通情况。

同时，为这些客户准备固定的公开网页材料和产品知识资料，使测试能够重复执行，避免每次互联网搜索结果变化影响问题定位。

测试样例可以覆盖以下情况：

1. **正常线索。** 有效且已分配负责人的线索触发研究，Agent 能够生成主要交付物。
2. **重复事件。** CRM 重复发送同一事件，系统不得创建多个相同任务。
3. **企业重名。** 搜索结果包含同名企业，Agent 需要根据可靠标识确认目标。
4. **信息不足。** 客户缺少公开资料，Agent 不得编造企业事实和采购需求。
5. **信息冲突。** CRM 历史记录与公开资料出现冲突，Agent 应指出差异。
6. **产品能力缺失。** 产品知识库没有某项功能，Agent 不得在开发资料中承诺。
7. **联系人缺失。** 没有可靠的个人信息时，Agent 应推荐相关岗位，而不是编造具体人员。
8. **用户修改。** 销售人员修改开发草稿后，Agent 应当保留修改并正确完成后续要求。
9. **权限限制。** Agent 尝试查询当前用户无权访问的客户时，工具必须拒绝。
10. **工具异常。** 搜索或 CRM 查询失败时，Agent 能够正确报告问题并保留有效成果。

测试时，需要记录每组输入数据、预期行为、实际输出以及主要错误，方便后续分析。

### 5.3 设计质量检查方法

对于结构和权限等比较明确的问题，可以通过程序检查。例如，任务是否重复创建、是否查询越权客户、主要报告字段是否齐全，以及引用的来源编号是否真实存在。

对于客户需求分析和开发资料，则需要结合人工评审。可以由具备销售经验的人员判断 Agent 是否识别了重要业务信号、需求推断是否合理、产品匹配是否准确，以及开发资料是否适合真实客户沟通。

特别需要区分两个问题：**来源真实存在，并不代表它能够支持 Agent 的结论。** 例如，一篇招聘新闻可以证明企业正在招聘某类岗位，但未必能证明企业准备采购相应软件。

因此，质量检查除了验证信息来源，还需要检查证据与结论之间的关系。

对于安全问题，应当设置独立的检查要求。跨客户越权读取、泄露内部沟通记录和未经授权对外发送消息，不能因为报告质量较高就被接受。

### 5.4 根据评测结果改进设计

假设在测试中，Agent 发现一家客户正在招聘 AI 工程师，便直接判断该客户具有明确的 AI 软件采购需求，并生成一份以近期采购为前提的开发方案。

我们需要进一步分析，问题究竟来自哪里。

如果模型已经拿到了正确的招聘信息，却将其错误解释为采购意向，那么主要问题可能出在需求分析规则或提示词。如果搜索工具返回了不属于该企业的招聘内容，那么应当检查企业身份识别和来源筛选机制。如果产品匹配错误，则需要检查内部产品知识及检索结果。

针对第一种情况，我们可以明确要求：招聘、融资、业务扩张和公开活动可以作为潜在需求的参考信号，但不能单独证明客户已有采购计划。对于明确采购意向，需要 CRM 沟通记录或其他可靠依据支持。

修改后，应重新运行原有测试样例，确认问题得到解决，同时检查是否影响其他客户的分析效果。

通过这种方式，我们可以逐步积累典型失败案例，持续调整提示词、工具设计和业务规则。

## 6、本课总结

通过这个案例，我们从一个 B2B 销售团队的业务需求出发，完成了一次相对完整的 Agent 产品设计。

首先，我们分析了用户和现有工作流程，明确客户研究、需求分析、开发资料和跟进策略之间的关系，并判断哪些任务适合交给 Agent 自主完成。

接下来，我们通过具体客户场景，设计了自动研究、信息来源管理、需求与产品匹配、开发资料生成、联系人推荐和产品信息问答等核心能力，同时明确销售人员应当在哪些环节参与判断。

在技术方案中，我们选择使用 Pi 作为 Agent Harness，并根据业务需求设计 CRM、互联网搜索和产品知识查询工具。CRM 事件和权限管理由确定性程序处理，Agent 在授权范围内自主选择搜索方向、分析信息并生成结果。

最后，我们将设计决策整理为产品需求说明文档，并建立相应的评测方法，帮助团队判断产品是否真正提高了销售人员的工作效率和研究质量。

整个设计过程中，我们需要始终关注一个问题：**为什么需要某项 Agent 能力，它解决了什么业务问题，又应该受到哪些约束？**

Agent 可以帮助销售人员更快地理解客户、整理信息和准备材料，但客户真实需求仍然需要通过沟通确认，对外联系和业务承诺也需要由销售人员最终负责。

通过这个案例，我们完成了从业务需求分析、产品方案设计、技术选型到需求文档和验证方法的一次完整实践。后续面对其他 Agent 需求时，也可以使用同样的设计思路，根据具体问题选择合适的能力、工具和实现方式。
