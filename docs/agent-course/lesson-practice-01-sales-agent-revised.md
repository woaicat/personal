# 实战演练：从 0 到 1 设计一个 B2B 销售助手 Agent

前面我们已经学习了 Agent 设计的主要知识，包括需求调研、模型选择、系统提示词、工具设计、上下文管理、人机协作和评测等。

但在实际工作中，我们很少按照课程目录，一项接一项地完成设计。
面对一个业务需求，首先需要弄清楚用户遇到了什么问题、希望如何解决，再根据具体情况决定需要哪些 Agent 能力，以及如何实现这些能力。

真实的设计过程通常围绕一个个需要解决的问题展开。例如，为什么这个需求需要 Agent？使用普通工作流能不能解决？Agent 应该自主完成哪些任务？哪些操作必须受到程序或人工控制？每一项技术决策都需要结合实际需求、资源和限制进行判断。

最终我们的目标是学会一种可迁移的 Agent 设计方法：如何从一个尚未明确的业务需求出发，通过分析、判断和取舍，逐步形成一个合理、完整、可落地的 Agent 产品方案。

这一课，通过一个具体案例，把前面学习的知识应用到实际的产品设计中。从最初的业务需求出发，逐步确定产品方案和技术方案，最终整理出一份可以交给开发团队讨论和实施的需求说明文档。

本课选择的案例是 **B2B 销售助手 Agent**。需求来自企业销售团队在客户研究和开发资料准备过程中遇到的实际问题，后续为了说明设计方法而补充的企业信息、客户资料和部分项目条件属于教学模拟设定。

学完本课，你将能回答：

1. 销售人员在客户研究和开发资料准备中，究竟遇到了什么问题？
2. 哪些工作适合交给 Agent 自主完成？
3. 哪些环节需要由 CRM 的确定性规则和销售人员控制？
4. 怎样用具体案例验证方案的效果与安全边界？

## 1、需求与背景

### 1.1 业务背景

某 B2B 软件公司向企业提供知识助手、智能客服和流程自动化等 AI 产品。销售人员接触新客户前，需要了解企业业务、近期动态和可能的产品需求，准备有针对性的沟通材料。

问题在于信息分散：线索和历史沟通在 CRM，企业介绍和动态在公开网页，产品能力在内部资料。销售人员花大量时间查找、核对和整理，仍可能把未经证实的猜测写进开发资料。

公司希望：**有效线索分配给销售人员后，系统自动研究客户并生成初稿；销售人员仍可通过对话追问和修改。** 本课的企业、线索和项目条件为教学模拟，不能视为真实客户资料。

### 1.2 用户与现有流程

第一版服务一线销售人员，销售主管工作台暂不纳入。我们先把销售人员收到线索后的工作拆开：

| 环节 | 需要回答的问题 | 常用信息 |
| --- | --- | --- |
| 了解线索 | 这是谁？此前谈过什么？ | CRM 资料、沟通记录 |
| 研究客户 | 客户做什么，最近有什么变化？ | 官网、新闻等公开资料 |
| 分析需求 | 哪些问题值得进一步确认？ | 客户事实、业务信号 |
| 准备沟通 | 首次联系说什么？ | 需求假设、正式产品资料 |
| 制定跟进 | 找谁谈，下一步问什么？ | 组织信息、已有联系人 |

这些环节相互影响。比如，连锁企业扩张门店可能引出培训与知识管理问题；如果 CRM 已记录客户咨询过知识助手，就应优先核对那次沟通，而非重新猜测需求。Agent 要减轻查找和整理工作，但销售人员仍负责确认真实需求。

### 1.3 为什么用 Agent

固定工作流也能完成“查资料—填模板”，适合来源稳定、步骤明确的任务。但本案例中，客户资料的分布和销售人员的追问都不固定：零售客户可能需要研究门店培训，软件客户可能需要关注技术路线；用户也可能只要求重写一段微信话术。

因此采用**固定业务规则 + Agent**：

| 由程序处理 | 由 Agent 处理 |
| --- | --- |
| 线索有效性、触发、去重、权限、任务状态 | 选择研究方向、调用只读工具、综合证据、生成与局部修改草稿 |

这不是让 Agent 接管销售流程。它可以决定下一步查什么，但不能自行认定采购意向、发送消息或改写 CRM 业务记录。

### 1.4 任务触发

**问题：** 确定采用 Agent 后，是否还要让销售人员每次手动发起研究？原需求希望新线索进入 CRM 后自动准备材料，因此触发条件应由业务系统判定，而不是让 Agent 猜线索是否有效。

第一版只有同时满足以下条件才创建任务：

- CRM 将线索标记为有效，且已分配负责人；
- 有可识别的企业名称或其他企业标识；
- 同一线索尚无同类型自动研究任务。

CRM 发出事件，服务按线索 ID 创建任务并去重。Agent 再读取授权信息。若外部搜索出现同名企业，需用官网域名、所在地和业务等线索核对；无法确认身份时暂停使用相关外部材料，请销售人员确认。这样把确定的触发规则留给程序，把不确定的研究判断交给 Agent。

### 1.5 目标与边界

产品目标是：在 CRM 客户详情页提供销售助手，自动整合授权的 CRM 信息、公开资料和正式产品知识，交付客户研究、潜在需求分析、开发资料及跟进建议，并支持后续对话。

第一版范围如下：

- **对象：** 单个有效线索及其负责人，不做批量研究和主管工作台。
- **信息：** 教学案例的 CRM 数据为模拟数据；外部信息须搜索核实；产品能力以授权资料为准。
- **行动：** 只研究、起草、回答和修改草稿；不发送邮件或企业微信，不修改 CRM 资料、状态及跟进记录。
- **表达：** 客户事实、需求假设、产品能力分别标明。业务扩张不等于采购意向，资料不足就列出待确认问题。

## 2、产品方案

现在用一条模拟线索，把能力落到具体任务中。

### 2.1 模拟客户

销售人员 A 收到线索 L-1024，企业为**澄远零售（虚构）**：CRM 标记为有效，已录入官网，历史沟通提到企业知识助手，但采购意向未确认。模拟公开资料显示，该企业近期拓展区域门店，并招聘门店运营岗位。

这条线索满足自动触发条件。Agent 的起点不是“写销售话术”，而是先确认企业身份、读取历史沟通，再决定哪些外部信息值得查。下文的客户动态和产品匹配仅用于演示设计方法。

### 2.2 客户情报

**问题：** CRM 知道销售关系，公开网页补充业务动态，两者都可能不完整。Agent 应先读取线索与沟通记录，再按研究目标搜索官网、新闻等资料。

报告只保留对开发有用的信息：企业概况、主营业务、近期动态、已有沟通和主要发现。重要事实附来源及时间；老新闻不能写成“近期动态”，同名企业的网页不能直接混用。

研究没有固定搜索次数：新线索可能值得追查，重复或低价值结果则应停止。公开资料不足时，交付有限报告并说明缺口，不能用想象填满模板。

### 2.3 潜在需求

模拟资料中，“拓展门店”来自公开信息，“培训资料管理分散”来自 CRM 历史沟通。Agent 可以据此提出知识管理需求假设，再查询正式产品资料核对能力：

| 层次 | 本例内容 | 写法边界 |
| --- | --- | --- |
| 已知事实 | 门店扩张；曾谈到培训资料分散 | 标明来源和时间 |
| 需求假设 | 多门店知识更新与员工答疑可能低效 | 使用“可能”，等待客户确认 |
| 产品能力 | 模拟资料中的知识助手支持文档检索、引用和权限控制 | 只写资料证实的能力 |
| 待确认 | 现有系统、使用范围、升级计划 | 留给销售沟通 |

交付的需求分析应列出“潜在问题—依据—匹配产品—待确认问题”。这样，销售人员能看到推理链，也能发现某项建议是否只是薄弱猜测。

### 2.4 开发资料

第一版优先生成微信沟通话术、电话提纲和简短产品介绍；邮件可按需生成。针对澄远零售，一句开场可以是：

> 了解到贵司近期在拓展区域门店，想请教一下不同门店的培训资料如何更新和使用。我们在企业知识检索方面有一些实践，如果这个话题与您当前工作相关，希望有机会交流。

这只是草稿。对外文字只能使用可公开的客户事实与核实过的产品能力；CRM 中未公开的内部沟通可指导销售判断，不应原样写进话术。

销售人员说“先谈业务，不要介绍产品”时，Agent 应只修改相关段落，保留已确认事实和人工编辑，无需重新开展整个客户研究。

### 2.5 跟进建议

**问题：** 销售人员需要知道先找谁，但公开活跃不代表采购决策权。本例可先建议联系运营相关岗位，了解培训和知识更新流程；再视情况联系信息化岗位，讨论系统集成与权限。

每条建议至少回答：推荐哪个角色、依据是什么、首次沟通要确认什么。若没有可靠的个人信息，只推荐部门或岗位，不编造姓名。后续“客户已有知识管理系统怎么办”等追问，应结合当前客户资料和正式产品资料回答，而非套用通用销售话术。

### 2.6 产品问答

销售人员也会直接问：“能否对接 OA？”“能否按部门设置权限？”“是否支持本地部署？”这项能力不依赖某条客户研究任务。

Agent 查询审核通过的产品文档后回答；在客户页面中可以结合当前场景解释，在独立问答中则直接回答产品问题。资料没有明确说明的功能、价格、交付周期或技术承诺，应标注无法确认并建议向产品或技术负责人核实。

### 2.7 人机协作

按行动后果划分责任，比让用户确认每一步更实用：

| 情况 | Agent 可做什么 | 人何时介入 |
| --- | --- | --- |
| 已授权的只读研究 | 自动查询、整理、生成草稿 | 无需逐次确认 |
| 企业身份不明或关键资料冲突 | 暂停相关判断，展示冲突 | 确认对象或补充证据 |
| 开发资料与跟进建议 | 生成、解释依据、按反馈修改 | 复核并决定是否采用 |
| 对外联系和业务承诺 | 第一版无发送与 CRM 修改能力 | 销售人员亲自执行 |

自主性用于研究和起草；客户沟通及承诺仍由销售人员负责。

### 2.8 工作界面

Agent 直接嵌入 CRM 客户详情页，不再新建客户管理平台。工作区需要让销售人员快速看到三件事：

1. **研究概览：** 当前状态、主要发现、失败或待确认原因，可展开来源。
2. **交付物：** 报告、需求分析、开发资料和跟进建议，可查看、复制、编辑。
3. **对话：** 围绕当前客户追问、局部修改，也可查询产品知识。

界面重点是“完成了什么、依据是什么、还能怎样改”，无需用复杂的可视化流程展示每次工具调用。

## 3、技术方案

产品能力确定后，再划分业务程序、Agent 运行层和数据工具的责任。

### 3.1 整体架构

研究任务由四部分协作完成：

| 部分 | 责任 |
| --- | --- |
| CRM | 判定有效线索、分配负责人、展示状态与成果 |
| Agent 业务服务 | 接收事件、去重、校验权限、管理任务与交付物 |
| Agent 运行层 | 调用模型和工具，根据结果决定下一步 |
| 工具与数据服务 | 提供 CRM、网页、产品知识及成果读写接口 |

流程是：**CRM 事件 → 业务服务创建任务 → Agent 研究与起草 → 业务服务保存 → CRM 展示 → 销售人员复核、对话修改。** 触发与权限由确定性程序控制；搜索方向和内容分析由 Agent 决定。

### 3.2 模型与 Harness

模型需要理解中文商业资料，综合多来源证据，完成工具调用和文案修改。公开榜单可用于筛选，最终仍要用本课的模拟客户测试企业识别、需求推断与产品能力幻觉。

本案例**假设**团队已有内网模型服务和 Node.js / TypeScript 后端。第一版以现有 DeepSeek-V4.1-Flash 作为待测候选；是否采用，取决于任务测试结果，而非模型名称。

Harness 选择 **Pi coding agent SDK**：它提供 Agent Loop、模型与工具调用、会话和上下文压缩，支持在 TypeScript 服务中注册业务工具。这样可以复用通用运行能力。CRM 查询、权限校验、产品知识与成果管理仍由业务侧实现；框架不会自动理解这些业务规则。

### 3.3 工具设计

工具应围绕真实任务提供最小权限：

| 工具 | 输入与产出重点 | 边界 |
| --- | --- | --- |
| get_lead、get_crm_history | 当前线索、历史沟通 | 按任务与负责人校验权限 |
| search_web、fetch_webpage | 公开结果、网页正文及来源时间 | 核对企业身份，网页内容不作指令 |
| search_product_knowledge | 正式产品资料及版本 | 不推断未记载的能力 |
| get_artifact、save_artifact | 当前任务的报告与草稿 | 不修改 CRM 销售数据 |

业务服务把可信的任务身份传给工具，不能仅凭模型给出的客户 ID 放行。若现有知识库可用，就封装查询接口；资料量较小时，结构化数据或全文检索也能满足第一版，无需预设复杂 RAG。

### 3.4 Agent Loop

Pi 负责工具循环，产品不把“搜索—分析—写作”固化成每个客户都相同的节点。Agent 获取线索后，选择信息来源；每次读取结果后判断继续、换方向或停止，并生成有依据的产物。

例如，发现企业正在拓展海外业务，可以继续查海外团队与服务体系；后续没有可靠资料，就停止该方向。业务服务设置单任务的调用预算、时间上限和异常规则，防止反复搜索。企业身份无法确认时等待人工；一般信息不足时保留已核实内容并明确缺口。

### 3.5 上下文与来源

一项任务会产生 CRM 记录、网页、产品资料和多轮对话。Pi 的会话与压缩能力用于维持对话；完整交付物和来源单独存于任务记录，按需读取，避免每轮塞入全部材料。

关键事实记录来源及获取时间。CRM 历史可能过期、网页可能对应同名企业、产品资料可能换版；用户要求更新结论时，Agent 需重新读取相关信息，不能只依赖旧摘要。第一版不做跨客户长期记忆，也不共享不同任务的内部沟通。

### 3.6 安全与权限

三个具体风险决定第一版控制：

- **越权读取：** CRM 工具校验线索归属与用户权限，Agent 不直接访问数据库。
- **外部内容诱导：** 搜索结果和网页正文只作为资料，不允许其命令 Agent 调用内部工具。
- **错误对外行动：** 第一版不注册发送邮件、企业微信或修改 CRM 的工具；开发资料中的客户事实和产品功能须有可核实依据。

权限在工具与业务服务中执行，不能只写进提示词。

## 4、产品需求说明

前面的判断可收束为一份简化 PRD，供设计和开发讨论。

### 4.1 基本信息

**产品：** B2B 销售助手 Agent，嵌入 CRM 客户详情页。**用户：** 一线 B2B 销售人员。**目标：** 减少客户研究与资料准备的人工工作，提高结论可信度和开发资料针对性。

第一版支持单客户自动研究、需求分析、开发资料、跟进建议和产品问答。它不自动联系客户、不改 CRM 业务数据，也不把需求假设写成明确采购意向。

### 4.2 业务流程

1. CRM 线索首次满足有效、已分配负责人及企业可识别等条件时，业务服务去重并创建任务。
2. Agent 读取授权 CRM 资料，核对企业，搜索公开信息和正式产品知识，生成四类成果。
3. CRM 展示状态、结果与来源；销售人员复核、人工编辑或通过对话继续修改。

若企业身份不明，任务暂停等待确认；局部资料缺失则显示缺口和已完成成果，不能伪装为完整研究。

### 4.3 功能需求

| 编号 | 能力 | 第一版要求 |
| --- | --- | --- |
| F01 | 线索触发 | 有效线索自动创建任务 |
| F02 | 任务管理 | 重复事件去重；展示状态、异常与重试 |
| F03 | CRM 查询 | 读取当前任务授权的客户资料与历史沟通 |
| F04 | 公开搜索 | 自主查找公开资料并保留来源、时间 |
| F05 | 客户报告 | 整合概况、近期动态与已有沟通 |
| F06 | 需求分析 | 写明假设、依据、匹配产品及待确认问题 |
| F07 | 开发资料 | 生成可编辑的微信话术、电话提纲和产品介绍 |
| F08 | 跟进建议 | 推荐有依据的岗位或人员与沟通问题 |
| F09 | 产品问答 | 根据正式产品资料回答问题 |
| F10 | 后续对话 | 围绕客户讨论并局部修改成果 |
| F11 | 可信提示 | 标明事实与推断，呈现来源、冲突和失败情况 |

具体接口和页面规则在实施文档中展开。

### 4.4 交付物

每条任务的成果关联线索 ID 与任务 ID：

| 产物 | 必含内容 | 用户操作 |
| --- | --- | --- |
| 客户调研报告 | 概况、业务、近期动态、CRM 历史及来源 | 查看、核对 |
| 潜在需求分析 | 假设、依据、匹配产品、待确认问题 | 判断、补充 |
| 客户开发资料 | 微信话术、电话提纲、产品介绍草稿 | 编辑、复制 |
| 跟进建议 | 推荐角色或可靠人员、理由、沟通问题 | 选择是否采用 |

来源记录需有类型、标题、地址或 CRM 记录 ID、时间及关联结论。产品问答在对话中提供，不额外生成文件。人工编辑不能被后续自动更新静默覆盖。

### 4.5 非功能要求

- **安全：** 线索与历史记录按权限访问，不跨客户泄露；没有自动发送和 CRM 修改能力。
- **准确：** 客户事实、产品能力有依据；推断标明不确定性，不编造联系人和采购意向。
- **可靠：** 重复事件、搜索失败、身份歧义和任务中断有明确状态，保留有效成果。
- **时效：** 外部事实记发布时间与获取时间，产品问答使用有效版本。
- **维护与排错：** 模型、提示词、工具和知识可分别更新；记录状态、错误、耗时、模型版本与来源。

### 4.6 验收标准

验收分三层，不把严重问题埋进平均分：

| 层次 | 检查重点 |
| --- | --- |
| 功能 | 触发与去重、授权读取、四类成果、查询与修改正常 |
| 业务质量 | 客户事实准确，依据能支持结论，产品匹配可靠，草稿有针对性 |
| 安全限制 | 不越权、不泄露内部资料、不未经授权发送、不编造关键产品能力 |

实际开发还需补充 CRM 事件协议、工具字段、页面细则、任务状态和异常处理。每项需求应能追溯到前面的业务问题；无法解释价值的能力，先不进入第一版。

## 5、验证设计

Agent 即使输出完整，也可能认错企业或把招聘信息误判为采购需求。验证应同时看任务质量与销售人员实际负担。

### 5.1 评测目标

| 维度 | 观察什么 |
| --- | --- |
| 任务质量 | 任务成功、客户事实、来源可追溯、产品描述与资料质量 |
| 工作效率 | 自动生成时间加人工核对、修改时间 |
| 使用情况 | 报告查看、草稿采用或修改、后续对话及销售反馈 |
| 安全可靠 | 错误企业、越权、编造、人工编辑丢失及工具异常 |

销售机会变化可在上线后观察，但受线索质量和销售行为影响，不能直接归因于 Agent。

### 5.2 测试数据

准备模拟 CRM 线索、固定网页材料和产品资料，使每次测试可复现。样例至少覆盖四组问题：

| 场景 | 期待行为 |
| --- | --- |
| 正常有效线索、重复事件 | 生成成果；同类任务不重复创建 |
| 企业重名、资料不足或冲突 | 核对身份；标明缺口与冲突，不编事实 |
| 缺少产品能力或联系人 | 不承诺未证实功能；只推荐可靠岗位 |
| 用户修改、越权查询、工具失败 | 保留人工编辑；拒绝越权；报告失败并保留成果 |

每例保存输入、预期、实际输出和错误，便于定位回归问题。

### 5.3 质量检查

程序适合检查去重、权限、字段完整性和引用是否真实存在。需求推断、产品匹配和沟通资料则由有销售经验的人员评审。

尤其要核对**证据是否足以支持结论**：招聘信息能证明企业招聘某类岗位，却不能证明它准备采购软件。越权读取、内部沟通泄露和未经授权对外发送应单独判为严重问题，不能被其他质量分数抵消。

### 5.4 结果驱动改进

假设 Agent 看到客户招聘 AI 工程师，就写出“近期明确采购 AI 软件”的开发方案。先定位错误发生在哪一环：

| 发现 | 优先检查 |
| --- | --- |
| 招聘信息属实，但推断过度 | 分析规则与提示词 |
| 招聘网页属于同名企业 | 身份核对与来源筛选 |
| 匹配了公司并无的功能 | 产品知识及检索结果 |

对第一种情况，规则应明确：招聘、融资和扩张只是潜在需求信号；明确采购意向需要 CRM 沟通或其他可靠证据。修改后重跑原案例及相邻案例，确认修复没有带来新的错误。典型失败案例也应进入后续测试集。

## 6、本课总结

通过这个案例，我们把一项模糊的销售需求推进为可讨论、可验证的 Agent 产品方案。主要收获是：

- 从销售人员的工作流程中找到值得解决的任务，明确产品目标和第一版范围。
- 划清 CRM、Agent 与销售人员的职责，设计自动研究、交付草稿和人工复核的协作方式。
- 用信息来源、产品资料和测试案例检查结论是否可信，并据此改进方案。

这条从业务问题到产品方案、再到验证与迭代的路径，也可以用于设计其他垂直 Agent。
